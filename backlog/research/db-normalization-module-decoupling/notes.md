# Notes: db-normalization-module-decoupling

Purpose: findings, the comparison of variants and the differences from the project's own practice.

## Findings

- Real FKs: feedback (content, rating, comment -> feedback/feedback_content), taxon (translation, assignment -> taxon), plus a self-FK user_information.deleted_by -> user_information(id) ON DELETE SET NULL (01-user-schema.xml) that the brief does not list. All are inside one module.
- Owner pair entity_type+entity_id in: attachment, attachment_snapshot, audit_log, contact_info, contact_view, feedback, feedback_aggregate, taxon_assignment, promotion_placement (9 tables, contact_view not named in the brief). EntityType enum: ADVERTISEMENT, USER, USER_SETTINGS, TAXON, PROVIDER_PROFILE, FEEDBACK, FEEDBACK_COMMENT.
- Marker defects found: attachment.entity_id and attachment_snapshot.entity_id say 'References advertisement(id), no FK' although the table is generic (ADR-003 attachment); promotion_placement.entity_id and contact_info.entity_id lack the word References; contact_view.entity_id has no marker; taxon_assignment.assigned_by and user_information.deleted_by (real FK) carry none - the ERD can therefore under- or mis-draw links. Hand-written link ATTACHMENT -> ATTACHMENT_SNAPSHOT in db_erd_conceptual_relationships_json() of generate-architecture-model.sh.
- Each starter runs its own SpringLiquibase bean (@AutoConfiguration after LiquibaseAutoConfiguration); the app master changelog is empty. advertisementLiquibase and providerProfileLiquibase still carry @DependsOn("userLiquibase") although ADR-064 removed the last cross-starter FK - a leftover ordering coupling: without the user starter those beans fail to start. A cross-module FK would need exactly this kind of ordering for every pair.
- Integrity today is held by orchestrator cascades: ProviderProfileSaveService.delete clears taxon assignments, contact, feedback, promotion in one transaction; AdvertisementSaveService.delete clears taxon assignments and soft-deletes attachments; UserDeleteService cascades ads, profile, api keys; UserCleanupService + UserPurgeEligibilityService replace the old RESTRICT/SET NULL (ADR-064). audit_log rows outlive their owner on purpose (history).
- Normalization proper (1NF-BCNF) is not violated by the owner pair: no repeated groups or transitive dependencies were found in the changelogs; the gap is declarative referential integrity across modules, plus deliberate derived data (feedback_aggregate). The plan must name this so 'normalize' is not read as 'add FKs everywhere'.
- Reusable: EntityExistenceService (orchestrator) already routes existence checks per EntityType to findExistingIds of AdvertisementPort/UserPort/TaxonPort/ProviderProfilePort; integration-tests level 2/3 run the orchestrator against real Postgres and TestDataCleaner knows every table; the generator already parses N-target markers ('References a(id) or b(id) depending on entity_type, no FK', audit_log and contact_view use it); contact 03 changeset is the precedent for fixing a remark with setColumnRemarks in a new changeset.
- ERD gap: liquibase-schema-to-json.js does not parse addColumn and the generator only includes files with createTable/setColumnRemarks, so contact_view.revealed_value (added by 02-contact-view-revealed-value.xml) is missing from docs/architecture/data/architecture-model.json (0 matches). A future purpose column added by a new changeset would be invisible too.
- Possible orphans not covered by any cascade: contact_view rows of a deleted provider profile or purged advertisement (ContactRepository deletes only contact_info). Whether contact_view is history (may outlive) or owned data is not recorded anywhere - decision for the person.
- Today only ADVERTISEMENT owns attachments (9 call sites, all EntityType.ADVERTISEMENT); only PROVIDER_PROFILE owns contact_info, feedback, promotion placements; no avatar exists (AccountNameViewModeHandler draws initials).
- Pre-check for step 2's name-pattern rule: after step 1, every column matching the pattern either has a real FK (user_information.deleted_by) or carries the marker (verified against all 12 changelogs), so the check starts green.

## Variants and comparison

- Source conflict recorded (followed one level deeper, then stopped): relational sources (GitLab, Karwin) optimise for declarative integrity inside ONE schema owner; modular/DDD sources (Microsoft, microservices.io, Jovanovic, Spring Data JDBC, Vernon) optimise for independent ownership and say integrity across owners is held by the API and eventual/app-level consistency. dev.to sits between: keep cross-module FKs with RESTRICT while one DB, drop when a module must rebuild alone - this project's starters must run without neighbours (ADR-064), which is exactly the drop condition. The conflict is a matter of what each optimises, not of fact.
- V1 link table per owner type with real FKs (Karwin reverse-the-reference, GitLab separate tables): best integrity; needs a FK across starters for every link (17 owner links in use today, 10 without audit history) plus Liquibase ordering between starters; a new owner type needs a new table + repository SQL; audit history cannot carry a FK (must outlive the owner). Biggest change, least decoupling, least flexibility.
- V2 owner registry / common super-table (Karwin solution 2): one owner_ref(entity_type, entity_id) table, children FK (entity_type, entity_id) to it; new owner type needs no child schema change. But the registry must live in some module (platform-commons has no schema), every owner and child starter then depends on it at DB level, owners must register/unregister in the same transaction, carrying data over needs one SQL reading every owner table, and registry -> owner is still held by code: the gap moves one hop. Medium-high change, one hub coupling.
- V3 exclusive arcs (one nullable FK column per owner type + CHECK num_nonnulls(...) = 1): integrity by DB, but every child table changes for every new owner type and every column is a cross-starter FK. Defeats ADR-003's generic owner.
- V4 reference by identity, hardened (Vernon, Spring Data JDBC no-FK option, Jovanovic, Microsoft, Rails Active Storage, Django GFK, dev.to 'three things replace the guarantee'): keep the owner pair; owner-side delete rule already exists in the orchestrator; add the two missing things - a mechanical check of the documented link (marker, no cross-module FK) and an integrity test that no owned row points at a missing owner; add a purpose column (Active Storage 'name') when a second kind of attachment arrives. Smallest change, decoupling unchanged (max), flexibility unchanged (max); integrity is detected, not prevented.
- V5 for point actor references only: real FK to user_information with RESTRICT (dev.to keep-while-one-DB). This is the exact constraint ADR-064 removed so user-spring-boot-starter's changelog runs alone; reopening it reverses an accepted ADR.
- Purpose of an attachment: (a) purpose column with default GALLERY (Rails name) - one table, owner pair unchanged, history per (owner, purpose); (b) a new EntityType per kind (USER_AVATAR) - mixes owner identity with role, breaks EntityExistenceService routing and audit; (c) a separate table per kind (GitLab separate tables) - clean but duplicates repository and port code per kind. (a) is the smallest; timing (now or with the avatar task) is the person's call.

## Differences from the project

- CONFLICT (early): relational best practice (GitLab, Karwin) says avoid polymorphic owner pairs and use per-parent tables with real FKs; the project forbids FKs across starters (guideline 7, ADR-064 marketplace-app, ADR-003 attachment, ADR-034 platform-commons). Modular-monolith and DDD sources side with the project (reference by id, no cross-module joins). Left to the person.
- Liquibase: the project edits unreleased changesets in place with validCheckSum ANY (ADR-064, ADR-051 marketplace-app) and also rolls forward (contact 02, 03); Liquibase's own guidance is roll forward once shared. The plan rolls forward (both are project practice); in-place editing remains a decision.
- Stale rule text: .claude/rules/integration-tests.md (lines 58-59) still says advertisement.created_by has an FK to user_information.id; ADR-064 removed it.
- Gap: the 'no FK across starters' rule exists only in ADRs (ADR-064 marketplace-app, ADR-003 attachment, ADR-034 platform-commons) and in per-starter rule files; root CLAUDE.md guideline 7 does not state it and nothing checks it.
