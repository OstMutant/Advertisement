# Notes: pluggable-modules-query-fragment-port

Purpose: findings, the comparison of variants and the differences from the project's own practice.

## Findings

- Single run with current indexes (R1-current-indexes.txt): the fragment F (EXISTS on taxon_assignment) uses the existing PK (entity_type, entity_id, taxon_id) as a correlated probe for the page and a hash semi-join for the count; plan time drops from 20-140 ms (A, bound array of 31k-241k ids) to under 1 ms. F behaves like B, not like A: fast pages for big categories (241k: 2 ms), slow pages for a rare category (3k ids: 360-485 ms against A's 54 ms), count about equal to A. Repeated five-round medians are running to replace these single-run numbers.
- Rare-category page explained from the plan: ORDER BY created_at DESC LIMIT 20 walks idx_advertisement_created_at backward and probes taxon_assignment once per scanned row; category 150 matches 1 ad in ~316, and the two parallel workers plus leader each run ahead (42 rows per process for a LIMIT of 20), so ~40,600 index probes are made. A does the same walk but tests membership in an in-memory hashed array, no probe per row, which is why A wins only this case.
- Failure modes demonstrated on temp tables (measurements/R5-failure-modes.txt): (1) an unqualified consumer column in a fragment silently changes meaning when the provider later adds a column of the same name (3 rows -> 10 rows, no error); (2) a consumer alias equal to the provider's internal alias is shadowed by the inner scope, silently wrong (10 rows); (2b) provider aliases starting with '_' while consumer aliases must start with a letter remove the capture; (3) a fragment placed outside its alias's scope (count wrapper) fails loudly; (4) a fragment containing OR appended without parentheses loses the consumer's own filter (0 expected, 3 returned); (5) UNION branches and (6) composite EntityRef keys and (7) ORDER BY placement all work; (8) a stale fragment after the provider table is dropped fails loudly.
- Data caveat found: in the first-pass data set created_at is random per row (pg_stats correlation 0.0035), while real advertisements are inserted in time order (correlation near 1). The rare-category page walks idx_advertisement_created_at backward and reads one heap page per scanned row, so this synthetic set is the worst case for F and B and the best case for nothing; a third phase re-runs everything after CLUSTER on created_at to show the realistic case.
- Five-round medians (planning + execution, ms per list page = page + count; A also pays its Taxon lookup, twice today, once in A1), final realistic state P3 = covering index + created_at in insertion order: rare 3k ids A 30 / A1 29 / F 104 / B 84; 6.3k A 52 / F 82 / B 74; 31k A 231 / F 219 / B 201; 66k A 323 / F 228 / B 239; 241k A 907 / A1 813 / F 334 / B 370; cat AND city A 171 / A1 100 / F 134 / B 107; OFFSET 1000 A 237 / F 276 / B 268; three cats 41k A 257 / F 210 / B 248. A excludes moving the ids through JDBC (not measured; a psql fetch of 242k ids took 300-400 ms in pass one). F is within noise of B everywhere: B's gain came from one statement, not from who owns the table.
- Covering index (taxon_id, entity_type, entity_id) helps F: the count's semi-join reads it index-only (31k: 234 -> 197 ms; rare 44 -> 27 ms; cat AND city 290 -> 85 ms in P1->P2) and it also serves the correlated probe; it helps A's lookup more (31k: 83 -> 10 ms server-side).
- Generic plans (forced, what pgJDBC can reach after prepareThreshold=5): F.page keeps the same good shape (rare 120 ms, big 0.9 ms); F.count always becomes a hash semi-join over a full scan (rare 165 ms vs 20 ms custom, 241k 684 vs ~333 ms); A is hit harder (page at 241k 1175 ms vs ~176 ms custom, count 1091 vs ~542 ms). The risk is shared by A and F and is not created by the fragment; whether the project's statements actually reach generic plans was not measured (unverified).

## Variants and comparison

- G (fragment shaped as a.id = ANY(ARRAY(SELECT entity_id ...)), built once inside PostgreSQL): good for the rare category (page 17 ms, count 15 ms) but bad for big ones (31k: 192 + 238 ms; 241k: 706 + 676 ms) because a non-constant array is searched linearly per row; not a general answer, kept as a measured reference.
- Theory map: the proposal is a Specification (Evans/Fowler) in its query role, owned and fixed by the provider (Khorikov's strongly typed specification, not a generic one carrying client SQL); technically a Query Object fragment (Fowler PoEAA) rendered to SQL; its closest framework analogue is Spring Data PredicateSpecification.toPredicate(From, CriteriaBuilder), where the caller hands in the root and the specification builds a predicate against it -- our SqlColumn plays the role of From. jOOQ's equivalent is a Condition built from QueryPart arguments ({0} templating) with values as binds. In database terms the result is a correlated EXISTS = semi-join (PostgreSQL docs), i.e. the provider's filter is pushed down into the consumer's statement (predicate pushdown, as postgres_fdw does across servers). In DDD terms Taxon offers it as an open-host service whose published language is SQL text -- which is exactly the shared-database coupling Fowler (IntegrationDatabase) and Grzybek (shared database = last resort) warn about; the warning is about schema knowledge leaking to other modules, which the provider-owned fragment confines to the provider's own code, but not about the shared runtime (same database, same role, same snapshot).
- G with a city filter is catastrophic: category 5 AND city 201 builds a second array of ~99k ids searched linearly per row; the five-round run spent over 15 minutes in it and was cancelled. G is therefore ruled out as a general fragment shape; its rare-category numbers stay only as the reference for a possible provider-side optimisation (step F8).
- Final comparison against the five goals: A (ids through Java) fails goal 3 and pays most at big categories (241k: 907 ms server-side plus JDBC transfer); B (local table) fails goal 2 by the user's own rule and is measured equal to F; F meets all five, at the cost of selective filters (3k: 104 vs 30 ms), a recorded-decision change, a platform-commons governance exception and runtime coupling to one shared database. Contract: typed SqlPredicate + SqlColumn in platform-commons core.model; query-lib reuse rejected (frozen API, would pull JDBC into platform-commons).

## Differences from the project

- Conflict flagged early: a Port returning SQL text contradicts taxon ADR-001 (Set<Long>, no SQL JOIN; its own revisit trigger names a starter-owned JOIN helper as the next option) and needs a refinement of app ADR-034 (no raw cross-starter joins). ADR-034's stated reason is a consumer hardcoding another starter's table names; with a fragment the provider writes its own table names, so that reason is answered for tables but not for the consumer's alias/column handed to the provider.
- Conflict flagged early: platform-commons governance lists 'Feature-specific models or persistence logic' as NOT ALLOWED and platform-commons has no spring-jdbc or query-lib dependency (checked platform-commons/pom.xml); query-lib ADR-003 freezes its API (no JOIN DSL, no expression AST). Any fragment type has to sit in one of these and needs an explicit exception from the user.
- Stop rule: the last sources (Spring JDBC source, pgJDBC docs, contextmapper) only refined details of the contract and failure modes; the choice turned on the measurements, and after the three phases (current index, covering index, clustered created_at) plus forced generic plans, no further experiment could change which variant meets all five goals, only the size of the selective-filter penalty, which needs production data.
