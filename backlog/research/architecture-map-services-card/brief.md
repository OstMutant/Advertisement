# Brief: architecture-map-services-card

Purpose: what the planner is asked to find out and plan; written by the main thread, read by the planner.

## Goal

Plan how to add a "Services" card to the System screen of the generated architecture map. The card opens a screen with one card per local web service; each card opens that service's page in a new tab. The plan must also move the hardcoded host ports into the repo-root `.env` so the generator reads every address from one place.

## Task

[improvement-228](../../tasks/improvement-228-architecture-map-services-card.md)

## Context

- The map is `docs/architecture/architecture-map.html`, generated by `docs/architecture/scripts/generate-architecture-model.sh` together with `docs/architecture/data/architecture-model.json`. The System screen is `renderSystem()` inside that script: five entry cards today (Tooling & Pipelines, Backlog, Diagrams, ADRs, Code Quality). Navigation is a router with `navigate({screen: ...})` and a growing breadcrumb stack.
- Web services and their host ports today: the app 8081 (default in `scripts/deploy-and-run/run.sh`, `APP_PORT`); Swagger UI at `/swagger-ui/index.html` and OpenAPI JSON at `/v3/api-docs` (springdoc in `marketplace-rest-api`); the API flow runner page at `/dev-tools/api-flows/` (only after `deploy-and-run.sh --dev-tools`, `DevToolsConfig`); SonarQube 9099 (literal in `scripts/sonar/docker-compose.sonar.yml`, dashboard `/dashboard?id=advertisement`); Dagu UI 8082 (literal `UI_PROXY_PORT=8082` in `scripts/ci/run.sh`, proxied to Dagu's own 18080); SeaweedFS master UI 9333 (literal in `scripts/deploy-and-run/docker-compose.seaweedfs.yml`).
- Only `DB_PORT` and `S3_PORT` are in the repo-root `.env` today. `INFRASTRUCTURE.md` holds a hand-written services table with the same addresses.
- Existing accepted decision: the System page holds only entry-point cards (find it in `.claude/nav/adr-index.md`, module `docs/architecture/scripts`); a sixth card needs that decision annotated or superseded, per the project's rules.
- The generator already talks to SonarQube at `http://localhost:9099` for metrics, so one address is already known to it.
- The project keeps one canonical home per fact: the addresses must not be restated by hand in a second place once the card exists; point the plan at which existing hand-written copies (for example the `INFRASTRUCTURE.md` table) stay and how they avoid drift.

## Completion criterion

Two plans in the topic folder: a human plan and a machine plan with numbered steps, the executor model per step, the exact files and edits per step, how each step is verified, and the cost. The plan must cover: moving the ports into `.env` with every consumer (compose files, scripts, `.bat` counterparts if they hold the same literal) updated; the generator change; the new screen and card; the ADR annotation; the documentation that mentions the addresses; and a verification path (generator run, freshness check, a screenshot or Playwright-free check of the new screen).

## Decisions already taken

- The generator reads host ports from the repo-root `.env` at generation time and writes a `services` list into `architecture-model.json`; the map only renders that JSON.
- The literal ports (9099, 8082, 9333, and `APP_PORT` if absent) move into `.env`; the files holding them read them back through `${VAR}` substitution.
- Only web pages get a card (app, Swagger UI, API flow runner page, SonarQube, Dagu, SeaweedFS master UI). PostgreSQL and the SeaweedFS S3 endpoint are not shown.
- No live status on the cards; they are plain links opening in a new tab.
- Out of scope: the CI stack ports (18081, 19333) and the Playwright report; static reports are a separate task.
