# improvement-244: Research: does the project need a wiki, and can an existing documentation tool replace the Architecture Control Plane, or is it better to keep it

**Type:** improvement — a research task, no code change until its result is decided
**Module:** `docs/architecture/` (the generated Architecture Control Plane), root `README.md`, `INFRASTRUCTURE.md`, all `README.md`/`DECISIONS.md` files
**Priority:** ⚪ low in effort (a research question, nothing is broken), at the top of the backlog at the user's request
**When:** independent, no blockers

## Current state

Checked on 2026-11-08:

- The project documentation is spread over 141 markdown files (outside `backlog/` and `.claude/`), 238 decisions in the `DECISIONS.md` files, 225 closed tasks in `backlog/completed/tasks/`, the root `README.md` (251 lines), `INFRASTRUCTURE.md` (189 lines) and `docs/best-practices.md`.
- `docs/architecture/architecture-map.html` is generated by `docs/architecture/scripts/generate-architecture-model.sh` from `pom.xml`, the Java source, the Liquibase changelogs, the `README.md`/`DECISIONS.md`/rules files, the backlog and the test and CI run data; it shows the diagrams (module dependencies, SPI map, database ERD, bounded contexts), per-module pages, the ADR list and the backlog.
- The root `README.md` is the entry for a newcomer: a "skim in 5 minutes" part and a table of the module documentation.
- A short web search on 2026-11-08 (standard mode, vendor pages and lists, not the tools' own documentation) found: Structurizr renders C4 diagrams and documentation from one hand-written model; Backstage TechDocs publishes markdown that lives next to the code in a central portal, and a community ADR plugin lists the ADR files of a repository with title, status and date; for MkDocs, Docusaurus and Read the Docs no 2026 comparison was found; no open-source Backstage plugin that draws relations between entities was found.

## Why change

The user asked whether a wiki would have been worth writing next to the Architecture Control Plane, and whether an existing wiki or documentation-site tool could replace the Control Plane and be more impressive, or whether it is better to leave it as it is. The question is not answered by the facts above: the search was narrow and did not compare the tools against what the Control Plane shows.

## Expected benefit

A decision, backed by checked facts: keep the Control Plane as it is, add a wiki, or replace the Control Plane, with the cost of each.

## Approach

Research only, with the `/deep-research` command or by hand, writing the result into a topic folder under `backlog/research/`:

1. Who reads the documentation (the owner, new developers, outside readers) and what each of them needs to find; asked of the user, not assumed.
2. What the Control Plane shows that is generated from the code (listed from the generator), and which of those parts each candidate tool can show without hand-written copies.
3. The candidates, each checked in its own official documentation: Structurizr, Backstage with TechDocs, MkDocs Material, Docusaurus, and any other found; for each, what it takes to keep it in step with the code.
4. The cost of each option against the rule that every fact has one home.
5. A recommendation with the options and the trade-offs, for the user to decide; no change to the documentation before that.
