# improvement-159: ADR system review & refinement — audit, threshold, template, migration plan

**Type:** improvement — documentation/process, analysis-first (no ADR content modified until
this issue's inventory is reviewed and approved)
**Module:** every `DECISIONS.md` file (16 files, 229 `## ADR-NNN:` entries total —
`advertisement-spring-boot-starter`/`provider-profile-spring-boot-starter`/
`user-spring-boot-starter` have none, generated pointer-only files), `docs/ai/adr-index.md`,
`docs/ai/scripts/generate-adr-index.sh`, `.claude/rules.md`
**Priority:** Top
**When:** independent, no blockers

## Problem

User supplied a full "Senior Software Architect ADR review" spec (9-step methodology: inventory
→ per-ADR classification → ADR-worthy threshold → format review → current-intent-vs-history
separation → AI-context evaluation → code-consistency check → minimization target → migration
plan). Confirmed against real repo data before filing:
- 229 `## ADR-NNN:` entries across 16 `DECISIONS.md` files; `marketplace-app/DECISIONS.md` alone
  holds 73 (largest concentration), `platform-commons` 29, `docs/architecture/scripts` 29,
  `audit-spring-boot-starter` 25.
- `Status:` field is highly inconsistent: ~200 plain "Accepted" variants (some with trailing
  whitespace), plus ~15 distinct ad-hoc "Superseded"/"Deprecated"/"Partially reverted" phrasings,
  several embedding long free-text notes instead of a clean pointer to the superseding ADR.
- `docs/ai/adr-index.md` (generated by `docs/ai/scripts/generate-adr-index.sh`) already provides
  a mechanical AI-retrieval index over every `## ADR-NNN:` heading — the spec's Step 9E ("AI
  retrieval rules") is already partially solved by this existing mechanism, not a green field.
- That index's own "Known gaps" section confirms the same 3 files with no `## ADR-NNN:` heading
  are unindexed — consistent with root `CLAUDE.md`'s note that these three ship generated
  pointer-only `DECISIONS.md` files with no hand-authored ADRs of their own.
- No existing ADR governs the ADR system's own structure/threshold/lifecycle.

## Suggested fix

Run the review scoped per module — 229 ADRs will not fit one context pass:
1. Pilot on the two largest files first (`marketplace-app` 73, `platform-commons` 29) to validate
   the classification approach before scaling to the remaining 14.
2. Delegate per-file inventory/classification (KEEP/MERGE/SUPERSEDE/DEMOTE/REMOVE/REWRITE, each
   with evidence) to subagents, one per `DECISIONS.md`, aggregate into one migration table.
3. Produce, but do not apply: ADR policy (when to create one), minimal template, the migration
   table, target structure, AI retrieval rules.
4. Wait for explicit approval on the inventory before touching any `DECISIONS.md` content —
   analysis-only in this issue's first pass, per the user's own framing of the request.

### Answer to "does this need doing at all"

Yes, consistently — every one of the 7 agents, working independently on different files with no
visibility into each other's findings, reached the same conclusion: real, bounded cleanup is
warranted. ~39% of all 229 entries (DEMOTE+MERGE+REWRITE+REMOVE = 91/229) are not clean, durable
architectural decisions as currently written — this holds regardless of file size, from the
73-entry `marketplace-app` down to the 3-entry `playwright`.

### Five recurring patterns, confirmed across the full corpus (not just the pilot)

1. **"Batch"/feature-slice logs split across sequential ADR numbers.** `marketplace-app`
   ADR-052...056 (leaf-UI refactor), ADR-059...062 (F-01 slices); `platform-commons`
   ADR-005/017/027 (Port-per-new-starter); `audit-spring-boot-starter` ADR-012/013/015
   (repository-method-naming evolution); `docs/architecture/scripts` ADR-016/018/019/025/026/028/029
   (a 7-entry saga tracking one diagram's rendering-technology churn) and ADR-022/031/032
   (script-header-convention evolution).
2. **"Correction-on-correction" accretion inside a single entry** — layered "Correction"/
   "Amendment"/"Refinement"/"Update" sections instead of a clean rewrite. Found in every file
   without exception; worst single case is `marketplace-orchestrator` ADR-004 (4 rounds of
   in-place revision) and `docs/architecture/scripts` ADR-029 (4 refinements + 3 bug narratives).
3. **Bug-fix/dependency-scope changelogs wearing full ADR ceremony** (DEMOTE-worthy) — especially
   dense in `integration-tests` (ADR-003/004/005/011, all environment/dependency-scope fixes) and
   `scripts` (ADR-010/011, CRLF/checksum bug writeups).
4. **"Addendum accretion"** — multiple unrelated decisions bundled under one ADR number via
   trailing addenda rather than sequential numbers (new pattern, not seen in the pilot):
   `scripts/ci` ADR-010 bundles 5-6 independent decisions (pipeline metrics, `--skip-vaadin`,
   param removal, a default flip, a new script) under one heading — worse for discoverability
   than the sequential-batch pattern since an index scan over `## ADR-` headings misses every
   addendum.
5. **Stale `Status:` fields where a later ADR (same file or cross-file) reverses the decision but
   the original's `Status:` was never updated** — at least 7 confirmed instances, a mechanically
   findable defect class:
   - `docs/architecture/scripts` ADR-015 — Status says "Accepted", body's own last paragraph says
     "Superseded by ADR-016."
   - `docs/architecture/scripts` ADR-028 — reversed by ADR-029 one entry later, Status still plain
     "Accepted."
   - `scripts/ci` ADR-002 and ADR-004 — Status "Accepted", but ADR-009 explicitly states it
     replaced both and the mechanisms "no longer exist" in code.
   - `scripts` (root) ADR-012 — Status says "Partially reverted" but the entry's own final section
     shows a full revert.
   - `marketplace-orchestrator` ADR-001 — never marked superseded despite ADR-004 reversing its
     core "never depends on a starter jar" rule.
   - `platform-commons` ADR-010, ADR-025 (pilot) — Status "Accepted" for content the entry's own
     body says was later removed.

## Step 3 resolution: threshold already existed — granularity gap fixed instead (2026-08-18)

Checked before designing a new threshold from scratch: `.claude/commands/decision.md`'s "Before
writing: is this actually ADR-worthy?" section already defines a repo-specific 3-condition
positive test (expensive to reverse / constrains future decisions / prevents re-litigating a
rejected approach) plus a negative list (bug fix, UI/layout, self-evident rationale) — spot-checked
against several of this issue's own KEEP/DEMOTE calls and it predicts them correctly. Step 3 does
not need a new threshold.

What the existing gate didn't cover: **granularity** — it answers "is this ADR-worthy at all," not
"should this be one entry or several." The single largest clutter pattern found in Steps 1-2 (the
sequential "batch"/feature-slice saga, e.g. `marketplace-app` ADR-052...056) is a granularity
failure, not a worthiness failure — each individual entry might pass the gate, but recording the
same decision's *progress* five times instead of its *outcome* once is what produced the mess.

Fixed: added a "One ADR per decision, not per work session/batch" paragraph to
`.claude/commands/record-decision.md`'s worthiness-gate section (renamed from `decision.md` in the
same pass — see below) — extend/supersede an existing entry for a continuation of the same
decision, rather than adding a new sequential number.

## Step 4 resolution: format is sufficient, added an update-discipline rule instead (2026-08-18)

Assessed against the original spec's own constraint ("do NOT add fields merely because they are
conventional — only recommend fields that materially improve this repository"): `Alternatives`
(already exists as optional `**Rejected alternatives:**`), `Evidence` (already present inline in
Context/Decision/Consequences throughout the corpus — "confirmed directly", specific file/line
citations), and `Related` (now covered by `docs/ai/adr-index.md`) all fail this test — none of the
229 ADRs' real defects were "missing field," so no new mandatory field was added.

The one real format-level defect the audit surfaced — "correction-on-correction" accretion
(layered `Correction`/`Amendment`/`Update` sections stacked in place, found in nearly every file) —
isn't a missing-field problem, it's a missing-discipline problem. Fixed by adding a "When a
decision changes, supersede — don't append a correction layer" rule to
`.claude/commands/record-decision.md`, right after the granularity rule: mark the old entry
`Superseded by ADR-NNN` and write a new, self-contained entry, rather than editing history in
place. This also partially answers **Step 5** (active vs. historical separation) for free — the
`Status: Superseded by ADR-NNN` convention, applied consistently going forward, already
distinguishes current intent from historical record without needing a physical archive/move (the
existing "append-only, never renumbered" character of `DECISIONS.md` stays intact); `taxon-
spring-boot-starter` ADR-004 was already confirmed as a model example of this pattern during
classification.

## Step 5 resolution: no physical archive file — confirmed (2026-08-18)

User raised the concrete alternative (a per-module `DECISIONS-ARCHIVE.md`, mirroring
`backlog/completed/`, with `adr-index.md` linking to it) and asked directly whether the in-place
`Superseded by ADR-NNN` convention would clutter things long-term. Weighed against real data:
only 15/229 (6.6%) ADRs are currently Superseded — not a volume problem yet. `DECISIONS.md` is
already not auto-loaded per session (`docs/ai/README.md`); `docs/ai/adr-index.md` is the real
entry point and already surfaces `Status` per row, so "AI shouldn't receive the full historical
archive automatically" is already satisfied without a physical split. A separate archive file
would reintroduce the exact "which of N files is this in" friction this issue's citation-decoupling
work just spent effort removing, and would break the several real cases found during
classification where understanding a *current* ADR requires reading the *superseded* one right
next to it (e.g. `docs/architecture/scripts` ADR-029 directly re-litigates ADR-016's finding).
**Decision: keep Status-in-place, no archive file** — revisit only if/when the active-ADR count
genuinely becomes unwieldy, at which point Step 8's actual DEMOTE/MERGE application (not archival
machinery) is the first lever to pull.

## Step 7 resolution: eager audit replaced with a lazy `Verified:` field (2026-08-19)

A pilot (2 agents, `marketplace-app` 48 + `platform-commons` 19 KEEP/REWRITE entries) was launched
to check every entry's claim against real current code, but both agents failed mid-run (process
exit, state lost, zero results — an infrastructure failure, not a task-design problem) and were
not retried. User then proposed replacing the one-time exhaustive sweep with an ongoing lazy
mechanism instead of either doing the full 148-entry audit or skipping verification entirely:

1. New optional field `**Verified:** YYYY-MM-DD` — a separate line right after `**Status:**` (kept
   out of `Status:` itself, deliberately, to avoid reintroducing the mixed-vocabulary Status
   problem Steps 3-5 just cleaned up). Absence means "never independently re-confirmed since
   written," not itself a red flag.
2. `docs/ai/scripts/generate-adr-index.sh` extended to parse it — `docs/ai/adr-index.md` gained a
   `Verified` column (238 entries regenerated, all blank for now — no entry has ever used the new
   field yet). One real bug hit and fixed while editing the script: an apostrophe inside a new awk
   comment broke bash's single-quote parsing (`syntax error near unexpected token`), unrelated to
   the actual feature logic.
3. New standing rule in `.claude/rules.md` ("Stamp an ADR's `Verified:` date whenever you happen to
   confirm it against real code") — opportunistic only, never its own dedicated audit task.

This converts Step 7 from a one-time expensive sweep (that goes stale again the moment it
finishes) into a continuously-refreshed signal accumulated for free across ordinary future work —
closes Step 7 by replacement, not by skipping it.
