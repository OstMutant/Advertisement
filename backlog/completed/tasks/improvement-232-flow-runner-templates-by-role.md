# improvement-232: API flow runner pages: templates by role (administrator, moderator, user) instead of Everything and Minimal

**Type:** improvement
**Module:** `marketplace-mcp`, `docs/api-collections` (`flow-runner/page/js/templates.js`, `templates-bar.js`, `main.js`, `rest-page.js`, `mcp-page.js`, `scripts/check-collection.config.json`, `scripts/run-flows.mjs`, `postman/*.postman_collection.json`), `playwright/e2e/11-api-flow-runner.spec.js`
**Priority:** high
**When:** independent. Touches the pages finished in improvement-221 Phase 2; does not depend on its Phase 3.

## Current state

- Both runner pages (REST `index.html`, MCP `mcp.html`) offer two built-in templates, `Everything` (all flows) and `Minimal` (a small fixed subset), plus templates saved in the browser. They are built by `builtIns(collection, {minimalFlows, minimalStepsOff})` in `flow-runner/page/js/templates.js`; each page passes its own lists from `rest-page.js` / `mcp-page.js`.
- The page has no notion of a role. The flow-runner design explicitly says there is no role selector and no automatic detection of roles: credentials sit in the flow settings and a step without rights returns its 403.
- A role exists only in the console run: `scripts/check-collection.config.json` has `"roles": { "user": ["Authentication", "Infrastructure", "Account"] }` and `run-flows --role user` runs only those flows. Every other REST flow (Taxons, Profile, Advertisements, Media, Contacts, Feedback, Moderation, Users) uses the administrator's key; the collection has no moderator key at all.
- The MCP collection needs no administrator: every flow runs with the key of a freshly registered user.

## Why change

`Everything` and `Minimal` say nothing about who the run is for. A developer wants to run what an administrator can do, what a moderator can do, or what an ordinary user can do, and see the flows that role covers, not a fixed "minimal" subset. The role split already exists for the console but not for the pages, and the MCP page has the same two generic templates.

## Expected benefit

One click runs the flows of one role on either page, the same split as the console run, with no administrator needed for the user template, and the list of flows per role kept in one place.

## Approach

The owner asked for the three roles administrator, moderator and user, on the REST and the MCP page, instead of `Everything` and `Minimal`. Decisions to take before work (options, not decided):

1. **Where the role lists live.** (a) In each page's profile (`rest-page.js`, `mcp-page.js`) and the console run reads the same source, so the lists exist once; (b) the page reads the console config, which is not served today. Either way `roles.user` in the config and the page template must not be two copies.
2. **What a role template is.** The set of flows (and steps) a role can run. For the REST collection this needs a moderator path: today no flow acts with a moderator key, so either flows get moderator steps or the moderator template lists the flows that only need rights a moderator has (Moderation).
3. **The MCP page.** Its flows already need no administrator. Role templates there mean running the same read tools with the key of a user promoted to moderator or administrator, which needs an administrator to promote them; decide whether the MCP page gets all three or only the one role that fits.
4. **`Everything` and `Minimal`.** Replaced by the role templates (the owner's wording) or kept alongside; `RESERVED_NAMES` and the saved-templates behaviour follow from this.
5. **Tests.** Extend the existing flow-runner spec (templates test) instead of adding a new spec; the console `--role` run is proven for each role on an empty database and a used one.

## Decisions taken (2026-11-01)

1. **Templates.** `Administrator` replaces `Everything` (all flows); `User` replaces `Minimal`; `Moderator` is added. `RESERVED_NAMES` and the README lines about templates follow.
2. **MCP is symmetric with REST.** The MCP server gets a tool for every REST operation (about 70; 11 read-only tools today), for every role, reads and writes; the MCP page gets the same three role templates as the REST page. Templates above the role of the key in use are shown but disabled; the role of the key comes from `getMe`. The earlier page design line "no role selector, no role detection" is dropped for this.
3. **Role lists come from the code, not typed by hand.** The two hand-typed lists (the page's `Minimal` lists in `rest-page.js` / `mcp-page.js` and `roles.user` in `check-collection.config.json`) go away; the page cannot read the config (only the page folder and the collection are served).

4. **The role of a step is the key variable it runs with (option A).** The collection gets a third key `{{moderatorKey}}`; every step a moderator may run switches from `{{adminKey}}` to it; `{{adminKey}}` stays only on steps only an administrator may run (role change, deleting another account). A role template = the steps whose key is that role's or a lower one; the role of a step is checked by running it with that key. The moderator is created and deleted by the run itself. Chosen over a role marker in the step description because role and key are then one fact, not two that can drift apart, and no new mechanism is needed.

5. **The `User` template also runs the flows that begin with `createTaxon` (Advertisements, Profile, Media, Contacts, Feedback).** What the user needs (category, city) is prepared and removed by the default administrator, who already exists in the collection (`email`/`password` variables). So a role template is defined by who performs the steps under test, not by every key in the flow; the `User` template needs the default administrator to exist.

6. **Preparation and cleanup steps are marked in the step header (option a).** A new header key (next to `step`, `label`, `kind`, optional `when`) marks the steps that only prepare or remove what a flow needs (for example the category and city of the Advertisements flow). They always run with the administrator key and belong to every template; `check-collection` validates the key. Chosen over separate Setup and Cleanup flows because flows stay self-contained and runnable alone, as the decision about repeatable flows requires, and the change is one header key instead of restructuring the collection.
7. **No administrator is not a stop, it is a choice.** When the default administrator cannot be used, the probe step no longer stops the run: it sets a run variable and shows a message offering two ways, enter the administrator's credentials (the existing `email` / `password` settings) or go on without everything that needs an administrator. Without credentials, every step marked in decision 6 and every step performed by the administrator is skipped as "condition not met" (shown skipped, not failed), and on the page the flows and templates that need an administrator are disabled with the same message. The separate no-administrator console run (`--role user` as defined today) is replaced by this.

8. **The MCP tools for every REST operation are Phase 1 of this task, before everything else.** The role templates, the key and header changes and the page work follow once the MCP side has all its tools and flow steps.

9. **Tests of the roles (option B).** The flow-runner Playwright spec is edited for the new templates, and `run-flows` runs once per role (user, moderator, administrator) in the CI e2e stage, so the flows of every role are proven in CI, not by hand. Further tests as required by the standing rules.

## Verified facts

- Every step of the REST collection already carries the key it runs with (`{{adminKey}}` or `{{userKey}}`); there is no moderator key.
- Privileged = administrator or moderator (`requireIsPrivileged`): taxon writes and feedback moderation. Nothing on the endpoints maps an endpoint to a role in a machine-readable way; only the `Role` enum and the checks inside the orchestrator services.
- The only conditional mechanism in the collection is `when: adminExists=no` (a run variable, not a role).
- A user cannot run the flows that begin with `createTaxon` (Advertisements, Profile, Media, Contacts, Feedback); a moderator can, so a moderator key runs them in full. The runner skips every step after the first failed one.
- The MCP module forwards the caller's `Authorization` header unchanged and holds no credential. REST issues an API key only with Basic authentication and registration is public, so key issuance through MCP needs a Basic-authenticated connection; to be checked in the code when planning.
- MCP first release deliberately excluded moderation, audit timeline, user administration, taxon writes, deletes, restores, contact reveals, key issuance and registration, with writes planned as a second wave; the coverage check requires every tool to have a flow step or an allow-list entry.
- Tests today: `check-collection`, `run-flows` (`--role user`), `api-collection-tests.sh` and the Node unit tests run by hand only; the Playwright flow-runner spec runs in the CI e2e stage, but as the administrator, so it cannot prove a role's flows work without an administrator.

Verified facts. In MCP mode `check-collection` counts a tool as covered only by a `tools/call` request to `/mcp` whose request name equals the tool it calls; every step id is used once; a label has at most 24 characters; `kind` is `required` or `optional`; `when` is `<variable>=<value>`. A write needs no category or city for an advertisement or a provider profile, so none of these flows needs a moderator. The flows mirror the REST flows of the same name (same step ids and labels where a REST step exists), but are smaller: one success step per tool and a few readable-error steps.

Conventions for every step (the standard shape of the existing steps):
- Request: POST `{{host}}/mcp`; headers `Content-Type: application/json`, `Accept: application/json, text/event-stream`, `Mcp-Session-Id: {{mcpSession}}`, `MCP-Protocol-Version: {{mcpProtocol}}`; body `{"jsonrpc": "2.0", "id": N, "method": "tools/call", "params": {"name": "<tool>", "arguments": {...}}}` with N the next unused integer in file order; request name = the tool name; request-level bearer auth `{{mcpKey}}` (the flow user), `{{mcpOtherKey}}` (the second user) or none; `issueApiKey` uses request-level Basic auth.
- Description header: `step: <flow>.<name>`, `label: <at most 24 characters>`, `kind: required|optional`, optional `when: <variable>=<value>`, then one sentence.
- Test script, three shapes, all starting with the one-line JSON-RPC parse used by the existing steps: **OK** (fails when `rpc.result.isError`), **OK+set** (OK, then `pm.collectionVariables.set(...)` of the captured values), **ERR n** (fails unless `rpc.result.isError === true` and the first text content starts with `HTTP n`).
- Captures: a write tool returns `structuredContent` = `{status, item, location, etag}`; a read of one item returns `{item, etag}`; a list returns `{items, totalCount}`. A version for `etag` is `item.version` (a write) or the `etag` field (a read); a plain number or quoted both work. A history list is newest first: the first element is the latest state, the last element the creation.
- New defaults copied from the REST collection: `pixelPng`, `videoUrl`; new runtime variables are named in the tables.

### Phase 2 - REST collection, keys and the runner (detailed design written 2026-11-01)

Verified facts behind the design (read from the code and the collection):
- The runner (`runner.js`) skips a step when `item.when.variable` differs from the run variable, with the note "condition not met"; one condition per step; a step whose `{{variable}}` is unresolved fails and the rest of the run is skipped. The parser (`collection.js`) reads a step header from the lines before the first blank line of the description; the keys it knows are `step`, `label`, `kind`, `when`; the folder description is free text.
- `check-collection.mjs` validates `step`, `label` (at most 24 characters), `kind`, and `when`; any other header key is ignored today. `run-flows.mjs --role` expands `roles.<name>` of `check-collection.config.json`.
- The REST collection has 11 flows and 145 steps. `{{adminKey}}` is the key of the default account (`email` / `password`), set by `auth.key` (when the login works) or `auth.adminkey` (after `auth.admin` registered the account); it is valid even when that account is not an administrator. The step `taxons.probe` lists users with it and fails with a message when the account is not an administrator.
- Steps by key today: Taxons, Users and Moderation use `{{adminKey}}` as the actor; Profile, Advertisements, Media, Contacts, Feedback and Moderation use it only to create and delete a category and a city (24 steps, four per flow); Authentication uses it to list and revoke the default account's own keys; `feedback.foreign` uses it as "a caller who does not own the profile".
- The old `taxons.probe` message tells the person to enter an administrator's e-mail and password or to run only Authentication, Infrastructure and Account.
- Spec `11-api-flow-runner.spec.js` refers to step ids (for example `users.flowdelete`), so no existing step id is renamed.

**Refinements of earlier decisions, settled by this design (the owner can veto):**
- **10. Templates are derived per flow, not per step.** Steps of a flow depend on each other (an id found by one step feeds the next), so cutting single steps out of a flow breaks the rest. The role of a flow is the highest role among its steps that are not helpers (the role of a step is the key it uses: `{{adminKey}}` administrator, `{{moderatorKey}}` moderator, any other key, Basic or no authentication: user). A template of role R holds every flow whose role is R or lower. The flows are written so that this holds.
- **11. The header key is `helper: yes`** (step header, next to `step`, `label`, `kind`, `when`). A helper step prepares or removes data or probes the account; it is ignored when the role of a flow is derived.
- **12. A flow-level condition.** The description of a folder may start with a header block `when: adminRights=yes`, a blank line, then the text; every step of that flow inherits the condition. Flows that cannot run without an administrator carry it, so they are skipped as a whole (not failed) when the default account has no administrator rights. The step `auth.rights` (Authentication flow, helper, no condition of its own) lists users with `{{adminKey}}` and sets `adminRights` to `yes` for 200 and to `no` for 403; it replaces `taxons.probe`.
- **13. Every moderator-level flow makes its own moderator.** Taxons and Moderation each start with helper steps that register a moderator, promote it with the administrator key and issue its key (`{{moderatorKey}}`), and end with a helper step that deletes it, so the flows stay self-contained and runnable alone.

**Flow roles after the change:** user: Authentication, Infrastructure, Account, Profile, Advertisements, Media, Contacts, Feedback; moderator: Taxons, Moderation; administrator: Users. Templates: `User` = the user flows; `Moderator` = those plus Taxons and Moderation; `Administrator` = all. The flows that carry the flow-level condition: Profile, Advertisements, Media, Contacts, Feedback, Taxons, Moderation, Users.
